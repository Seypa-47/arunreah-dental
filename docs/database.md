# Database schema

## Conventions

- D1 uses text primary keys generated by application code.
- `created_at` and `updated_at` are UTC ISO-8601 text timestamps.
- Public CMS records use `DRAFT`, `PUBLISHED`, or `ARCHIVED` status.
- Translated editorial fields use explicit `_en` and `_km` columns.
- Images/files are represented by R2 object-key columns only. No binary data is
  stored in D1.
- Foreign keys default to `RESTRICT`. CMS records should be archived instead of
  deleted when referenced. The optional appointment doctor reference is the
  deliberate exception: it becomes `NULL` on doctor deletion while preserving
  the appointment snapshot.

## Entities

| Area                 | Tables                                                                          | Notes                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Administration       | `admins`, `admin_sessions`, `admin_login_rate_limits`                           | Admin roles, credentials, opaque hashed session-token metadata, and login-rate-limit state.                           |
| Settings             | `clinic_settings`, `contact_settings`                                           | Singleton-style configuration records; application enforcement of one record is deferred to future settings services. |
| Public CMS           | `branches`, `services`, `doctors`, `showcases`                                  | Slugged bilingual content with publication status and display ordering.                                               |
| Content children     | `service_benefits`, `doctor_expertise`, `doctor_education`, `showcase_sections` | Ordered bilingual child content.                                                                                      |
| Related content      | `service_related_services`, `doctor_related_doctors`, `showcase_related`        | Ordered self-referential relations with unique source/target pairs.                                                   |
| Appointment requests | `appointments`                                                                  | References service, optional doctor, and branch; preserves names as historical snapshots.                             |

## Relationships

```text
admins 1—* admin_sessions
admins 1—* appointments (status_updated_by_admin_id, optional)

services 1—* service_benefits
services *—* services through service_related_services
doctors 1—* doctor_expertise / doctor_education
doctors *—* doctors through doctor_related_doctors
showcases 1—* showcase_sections
showcases *—* showcases through showcase_related

appointments *—1 services
appointments *—0..1 doctors
appointments *—1 branches
```

## Appointment integrity

`appointments.status` has a database check constraint permitting exactly:
`PENDING`, `CONFIRMED`, `COMPLETED`, and `CANCELLED`.

Appointments require a service and branch. Doctors are optional, allowing a
patient to submit “no preference.” Service, doctor, and branch name snapshots
preserve historical context when CMS content is renamed. Service and branch
deletion is restricted while appointments exist; an optional doctor reference
may be nulled without losing the doctor-name snapshot.

## Indexes

The schema indexes published content lookups by slug, status, featured/homepage
flags, and display order. Appointment indexes support inbox status filters,
preferred-date review, service/doctor/branch filtering, and chronological
ordering by creation time.

## Migration workflow

Generate migration SQL with `pnpm --filter @arunreah/api db:generate`. Apply the
committed migration local → staging → production. Never modify an already
applied migration; create a corrective migration instead.
